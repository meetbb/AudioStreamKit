# 2026-09-16

## Changed

- Implemented `AudioPlayer` (the public actor facade) per `public-api.md`
  §3: every method delegates straight to `PlaybackEngine`; it owns the
  framework's one `AsyncStream<PlaybackState>`, handing the continuation to
  `PlaybackEngine` at construction and finishing it in `deinit`;
  `CacheConfiguration` is wired into `MediaCache`/`MediaSource` at `init`.
- Made `PlaybackState` `public`/`Sendable` — required for `AudioPlayer.states`
  to compile; both were already specified in the accepted docs, just never
  applied since nothing crossed an actor boundary with it until now.
- Reviewed and trimmed comments across `PlaybackEngine.swift`,
  `PlaybackError.swift`, `FailureClassifier.swift`, `MediaSource.swift`:
  removed development-history narration ("caught in review" / "used to..."),
  keeping the underlying technical reasoning; fixed a stale comment in
  `FailureClassifier.classifyAsset` that claimed `MediaSource` didn't exist
  yet; compressed `MediaSource`'s class doc to point at
  `concurrency-model.md` §3 instead of restating it; rewrote
  `refreshNowPlayingInfo`'s doc comment into two short labeled sections.

## Decisions

- No unit tests added for `AudioPlayer` yet. It constructs its own
  `PlaybackEngine` internally with no injection seam, so testing its
  delegation meaningfully needs either an integration test against a real
  asset/server (the same gap already noted for `PlaybackEngine`) or an
  internal-only override point added purely for testability — deferred
  rather than decided casually.
- Multi-instance `AudioPlayer` support (arbitrating the shared
  `AVAudioSession`/`MPRemoteCommandCenter` across concurrently active
  players) is explicitly out of scope for V1, deferred until the planned
  consumer iOS app surfaces a real need for it.

## Known limitations

- `AudioPlayer` has no tests of its own — see Decisions above.

## Next

- Add integration tests for `MediaSource`/`PlaybackEngine`/`AudioPlayer`
  against a real asset or server.
- Build the consumer iOS app against `AudioPlayer`; use what that surfaces
  to decide if/when multi-instance support is actually worth adding.

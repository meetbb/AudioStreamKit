# 2026-09-21

## Issue found in the consumer app

While testing TrivaStream (the consumer iOS app), seeking during playback
left the player stuck in the `.buffering` state. The audio itself kept
playing from the new position, but the app's UI stayed on its loading
spinner indefinitely. (GitHub issue #1.)

In plain terms: the sound was correct, but the framework kept telling the
app "still loading," so users saw a spinner over working audio.

## Cause

Seeking while playing always moves the player to `.buffering`. It only
returns to `.playing` when AVPlayer reports that it changed to playing.
For a short seek, or one into audio that is already downloaded, AVPlayer
never stops playing, so it never reports that change and the framework
never got the signal to leave `.buffering`.

## Changed

- `PlaybackEngine.seek(to:)` now checks once the seek finishes. If the state
  is still `.buffering` but AVPlayer is already playing, the engine ends
  buffering itself. If AVPlayer really is re-buffering, the existing signal
  still handles it as before.
- Added an integration test that plays a real track, seeks, and checks the
  state returns to `.playing`. It fails without the fix and passes with it.

No public API change. The state machine rules are unchanged.
